# CMO Workbench 产品介绍

2026 年 11 月 24 日

同样是把工作交给 AI，有时我们会说「在这个仓库修好登录问题」，有时会说「以后每周跟进这几个客户反馈，有重要变化告诉我」。前者需要明确的项目、改动范围和验收结果，后者需要有人持续记住目标、跟进变化、在需要判断时找回来。这两种用法，对产品怎样组织上下文和工作进度提出了不同要求。

## 四款 Agent 的功能与定位

### Grok Bot

Grok Bot 把有名字和职责的 Bot 做成侧栏里的联系人。用户可以让 Bot 用云端电脑里的浏览器、文件和已连接的工具完成工作，也可以把重复操作设成例程。Team Bot 可以由多位同事共同使用，在 Slack 或 Microsoft Teams 等渠道协作。让同一个 Bot 长期承担调研或跟进职责，用户下次就能通过联系人名单找回原负责人，继续交代工作。 [Grok Bot 设计文章](https://x.ai/news/designing-grok-bot) · [Grok Bot 1.0](https://x.ai/news/grok-bot-1-0) · [Grok Bot 帮助文档](https://docs.x.ai/grok-bot/faq)

### Meta Muse

Muse 从个人目标和日常沟通出发。用户可以在 Muse 应用或 WhatsApp 里交代任务，让它处理旅行安排、邮件和预约，也可以把训练等长期目标交给它制定计划并持续跟进。Muse 在隔离的云端虚拟机上工作，可以使用浏览器和已连接的服务，较长的任务在用户关闭应用后仍可继续，遇到需要批准的操作会回来询问。它把个人助理的入口放在熟悉的消息渠道里，让目标、偏好和临时变化可以在日常交流中逐步补齐。 [Meta 发布说明](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/) · [Muse 功能介绍](https://ai.meta.com/muse/)

### OpenAI dots

用户可以在 ChatGPT 里创建一个持续工作的 dot。它有独立的云端电脑和浏览器，可以利用相关的历史对话、用户偏好和已授权的应用来研究资料、准备文档或推进跨项目的工作。用户能边执行边补充要求，也能在 ChatGPT 或已接入的 Slack 找到同一个 dot，并让它把需要判断的事项发到指定渠道。这套设计把 ChatGPT 里已积累的背景接到后续执行上，用户换了沟通渠道，手里的事仍能继续。 [OpenAI 发布说明](https://openai.com/index/introducing-dots/) · [dots 使用指南](https://learn.chatgpt.com/docs/dots)

### TRAE 宝

TRAE 宝同时提供「全局助理」和「项目助理」。全局助理跨项目查找历史对话、任务和产物，整理以前采用过的方案与约束。项目助理在具体项目中理解代码和要求，拆分可并行的任务，组织联调并汇总成果。最近任务和产物可以在助理工作台查看。接入飞书或微信后也可以收发任务消息，官方文档所述的手机使用场景需要桌面端运行且电脑保持唤醒。 [TRAE 宝官方文档](https://docs.trae.cn/ide_personal-assistant)

## 与 Codex 项目和对话体系的区别

以 Codex 桌面端的本地代码项目为例，项目提供代码目录、项目规范和工作环境，每条对话围绕一个交付目标展开。比如同一仓库里分别开两条对话来修登录问题和更新安装文档，各自保存讨论、执行过程和结果。Git 工作树（worktree）可以给并行改动提供独立的检出目录，用户可以在对话里检查代码差异。Codex 也支持云端任务和定时执行，因此是否能后台工作，与产品用什么来组织工作是两个问题。 [项目与对话](https://learn.chatgpt.com/docs/projects) · [Codex 运行环境](https://learn.chatgpt.com/docs/environments/modes) · [Codex 应用发布说明](https://openai.com/index/introducing-the-codex-app/) · [定时任务](https://learn.chatgpt.com/docs/automations)

| 产品 | 一次典型的委派 | 下次从哪里接着做 |
| --- | --- | --- |
| Grok Bot | 让研究 Bot 持续跟进竞品，例会前给小组更新 | 同一个团队 Bot，在工作群里补充要求或看进展 |
| Meta Muse | 下周出差，帮我调整个人行程和训练安排 | 同一个个人助理，在日常消息里告诉它变化 |
| OpenAI dots | 接着跟进 ChatGPT 里梳理过的发布计划，有阻塞就找我 | 同一个 dot，可在 ChatGPT 和已连接的渠道继续 |
| TRAE 宝 | 查找其他项目用过的权限方案，在当前项目落地 | 先从全局助理找背景，到项目助理查看任务和交付物 |
| Codex | 在这个仓库修好登录问题，跑测试并给我看改动 | 回到该项目的任务对话，核对代码差异和验证结果 |

核心区别是**上下文主要跟着什么走**。项目和对话把改动目标、涉及的文件、验证结果放在清楚的边界内，便于并行开发和逐项审查。常驻角色保留职责和与之相关的历史，减少长期工作中重复交代背景的成本。委派持续的时间越长，用户越需要知道每件事进行到哪一步、什么时候该自己决定。TRAE 宝说明这两种设计可以同时成立，助理负责接住上下文并调度，项目仍然提供执行边界。

## CMO Workbench 的设计理念

CMO Workbench 是面向日常办公和 CMO 业务的 Windows 工作台。用户从总台查看今天的安排，也能进入日程待办、办公助理或业务页面查看资料和办理事项。办公经常从一条消息、一场会议或一张表单开始，事情的状态也会随着人工操作和业务系统更新。CMO 因此把协作落在具体业务记录上，用户和 Bot 可以各自完成擅长的一段，再把同一件事交回去。 [产品原则](../PRODUCT.md) · [AI 原生工作区](requirements/shared/ai-assistant/ai-native-workspace/proposal.md)

### 工作台承载业务，Bot 承担持续职责

工作台保留用户可直接操作的日历、事项列表、材料和表单。Bot 按职责组织。总管做跨领域协调和结果汇总，日程助理管理日程和待办，办公助理处理工作消息、邮件和简报，配置管理管家负责权限管理、交付件管理、PBI 和 DTS 四个业务入口。各 Bot 保有自己的主对话和工作记录。主窗口和桌面灵动岛接到同一个总管对话，本机后台在窗口收起后仍能继续处理任务。配置管理管家已接入权限和 PBI 入口，交付件系统和 DTS 业务接入仍在建设中。 [角色与业务范围](../shared/bot-contracts.ts) · [工作台交互合同](../UX-CONTRACT.md)

### 人与 Bot 以同一份业务记录为准

业务页维护当前状态。以总台看板为例，用户保存卡片的位置后，可以让总管修改同一张卡片的样式，调整后的卡片会出现在原来的看板上。询问卡片里的日程和待办统计时，总管查询与看板同口径的数据。 [总管看板设计和验收](requirements/shared/ai-assistant/coordinator-dashboard/proposal.md)

### 对话交代意图，工作记录留下执行结果

同一条主对话可以连续讨论多件事。用户可以从相关消息打开单项工作详情，查看它目前在等确认、执行中，还是已经收到系统返回的结果。待办写入、WeLink 写命令和 PIC 群组申请提交等已有流程会先展示待执行的内容，由用户确认。群组申请的提交回执说明申请已经送达，后续审批有自己的状态。 [操作卡与确认流程](../UX-CONTRACT.md) · [Bot 架构与回执](requirements/shared/ai-assistant/bot-architecture/qa.md)

## 一条办公事项怎样变成待办

假设 WeLink 有一条消息请你最晚周五补齐评审材料。你在办公助理的「待处理」里打开这条事项，查看原文，再点「生成待办建议」。办公助理把建议放到自己的主对话里，你核对后点击「应用所选」，正式记录进入「日程待办」。回到原办公事项，还能看到它与已创建待办的关联。 [办公事项与原文](requirements/shared/ai-assistant/office-materials/spec.md) · [待办建议交互](../UX-CONTRACT.md)

下一步要贯通的是对话和界面的双向接续。按这个设计，你选中原消息后可以直接说「帮我建个周五到期的待办」，也可以在日程页把确认后的待办改为周四。回到办公助理问「这件事什么时候到期」，它沿原消息和待办的关联查到这条事项，读出刚保存的周四。人在界面与对话之间切换，工作始终接着同一条记录推进。 [办公事项接续计划](requirements/shared/ai-assistant/ai-native-workspace/plan.md)
