## 2 WeLink 对比结论

### 2.1 会议与邮箱日历合并

对方保留两处来源的原始记录，仅对展示行及交给模型的材料执行 `mergeMeetings`：

- 候选来自不同来源；标题转小写并移除空白、标点、符号后相同。
- 开始时间相差不超过 60 秒，结束时间也符合比较条件；代码允许两条结束时间均未知时匹配。
- 显示为一条并标明 WeLink + 日历，保留两个原始出处；没有确证共享身份。
- 已在简报、会前材料和会议查询工具使用，不只是未调用的辅助函数。

这是启发式合并显示，可能误合并同名同时的不同会议，也可能漏掉主题不同或时间调整过的同一场会议。“展示分组”在这里就是两条记录显示为一场，标记两处来源；不是另造可展开分组界面，对方也没有因此成为独立的分组管理功能。

按用户本轮决定，CMO 已采用同类规则，并额外限制同账号、同全天属性、一对一匹配。首页、日／周日程、顶栏和灵动岛日程合并显示，AI 的 displayEvents 返回展示项及两个原始 sources；详情优先使用邮箱日历记录，以保留按需读取详情的能力。底层仍按原记录保存。两个结束时间都未知时可合并显示，一个缺失而另一个已知时不匹配。CMO 在两条记录有完整有效时间且彼此都是唯一候选时，共用本地提醒、稍后提醒和完成状态；不会改变两个同步 ID 或修改远端。

### 2.2 安装、登录与连接维护

双方均调用 welink-cli，不是两种不同的 WeLink 服务端接入。CMO 优先使用内置 CLI，其次使用 WeClaw 所带 CLI 和 PATH，提供扫码登录及状态读取。对方另外提供多版本发现与选择、内部源安装与包完整性检查，以及独立 AuthKeeper：定期复查，失效时尝试登录续接，需要扫码则停止本次尝试并提示。只有只读查询可以在恢复后重放，发送命令不因此自动重放。两者都不能绕过真正需要人的扫码授权。

用户决定继续随安装包自带 CLI，不扩展多版本选择或内部源安装。CMO 已在现有轮询加上连接状态识别、失败退避、扫码提示和恢复后的补读；继续复用 CLI 自带的凭证刷新。日程页读取当前显示范围，分别显示两路状态，可按需展开会议详情。见 [CMO 日程同步说明](../../../welink-calendar-sync.md)。未引入完整 AuthKeeper，也不会自动重放发送命令。

### 2.3 按需查询与持续采集

CMO 已持续同步个人日程；私聊、群聊和邮件主要在用户提问后，通过 AI 的 welink_run 按需读取。对方另有应用级采集器，即使没有用户提问，也按间隔更新最近消息和未读邮件，消息用游标与本地缓存补取增量。默认快照回看 36 小时；另有夜间消息归档任务，首次按服务器可得范围回补，之后增量归档。源码中的约 100 天为其环境依据，不能当成所有账号通用的服务器保证。

采集、保存不等于一直调用模型。规则可先产生清单，需要语义分类、简报或回答时才调用模型；历史材料按问题筛选后送入，不是每轮把本机全部档案放进上下文。

分析对象是已取得的会议、日历、私聊、群消息、邮件，以及本人明确记录的偏好和承诺。例如从“周三把方案给你”提取承诺，从未回复的问题中找待办，从相关消息与会议议程中形成会前准备。规则和模型共同判断，推断必须与原话事实区分，不能因为最后一句是对方发的就一律催回复。

### 2.4 提醒与写入边界

CMO 现有提醒围绕已保存的事项、日程和外部 Agent 回复。对方还从消息及邮件推导提醒条件：等待回复过久、承诺将到期、关键词命中、会议冲突或连续过密；加入去重、工作时段和通知限额。其规则通常每分钟检查，不是每分钟都让模型阅读全部材料。

对方公司助理的 WeLink 工具按查询白名单放行，正常问答可以产生草稿，不能任意发消息、发信、创建会议或改日历。完整可追到的发送通道是主进程向用户指定的手机群发文字，群号须与放行参数一致。welink.js 另有 sendUser 受限私聊放行代码和注释；已读的主服务、页面与 IPC 未找到对应发送调用，不将其列为已完成的页面功能。会议室组件等独立业务写入不受“公司助理只读”这一产品描述概括。

上轮发现 CMO 装配时传入 undefined，导致 WeLink 兜底确认未接通。本轮已修复：读取命令白名单直接执行；发送、创建、修改、删除、上传及未知命令由 welink_run 展示本次完整参数后等待确认，取消、停止或没有回调均不执行。确认参数使用执行前快照，不让确认期间参数变化替换接收人或正文。不再要求模型先调一次 declare_write，以免同一次执行重复确认；真正的业务成功仍须检查 CLI 返回。

WeLink 执行前复核用户确认时的登录账号和参数。待办通过建议卡及 applyPlan 检查事项版本，PIC 的 group_submit 在提交时复核已确认的表单。通用 browser_act 保留声明确认，并在能识别提交时交由用户接手。网页自定义行为仍需按具体业务适配，详见[写入边界与后续设计](office-materials-and-bot-workspaces.md#6-写操作的现状与后续设计)。

### 2.5 消息提醒第一版及后续优化

入口暂放「设置 → W3和Welink接入 → 消息提醒」，结果复用灵动岛提醒及原话列表；本轮不新增导航工作台。

- 默认关闭；开启后每 10 分钟只读查询最近 20 个会话，每轮每会话最多 100 条，保留近 36 小时、最多 2000 条本机材料。已有游标从已消费边界补取，范围受限与失败明确显示，不宣称覆盖全部聊天历史。
- 私聊的明确请求、群内 @本人的问题等待默认 4 小时后形成「可能待回复」。后续回应明确引用原请求时可自动解除，未关联的发言标为待核对，可在办公助理复核。
- 本人承诺中有明确日期且到达当天，形成「核对承诺」。规则保留原话已有的日期精度。识别入口使用近期消息，已记录承诺可在台账跨日跟进，关联待办后使用该事项的日期和状态。
- 别人发来的关注词消息可提醒。按账号／会话／消息／类型稳定去重，处理与提醒回执持久保存；每小时最多 3 条，先承诺、再待回复、再关注词，沿用既有免打扰行为。
- 取数不完整的会话暂停待回复／承诺推送，取数失败不推送缓存旧判断；账号切换、停止或超时期间的迟到采集不得写回本轮结果。缓存损坏保留原文件并报错。
- 展开候选可查看发送人、会话、时间、消息编号和原话；“已处理”只收起本地候选，不向对方发消息，不自动创建待办或断言承诺已兑现。

值得继续做的优化：统一消息／邮件原始身份与覆盖范围；按用户关注会话持续采集与归档；为“待回复、承诺、会前准备、周报”分别准备材料、输出格式和来源核验；确认后转入现有待办，再由已有完成、稍后提醒与时间管理功能跟进。

CMO 可复用的优势是现有日程／待办及完成闭环、双来源同步的独立状态与失败缓存、浏览器业务执行，以及已有写入工具和确认界面。对方较完整的是自动准备办公材料、专用场景规则和持续分析，不应把 CMO 现有临时问答说成完全没有总结能力。

完整公司助理以后适合有一个集中入口，容纳待回复、承诺、简报、证据和任务进度；该入口是同一个长期 Bot 的办公视图，WeLink 手机群也路由到同一身份和主对话。先完成数据与提醒，再按信息量决定是否新增工作台，避免把一个开关独立做成大页面。

本轮验证：WeLink、日程计数与设置相关测试 85／85 通过，字体检查、前后端类型检查与构建通过。隔离 Electron 使用虚构 CLI 返回验证开启、原话展开、已处理、失败保留与重试、双来源一场显示、1024×680／1280×820 和 mist／cool／warm 主题，未调用真实消息发送。全量当前 893 项中 49 项失败；修改前提交隔离对照 877 项中 59 项失败，按测试名称比对无新增失败项。现存测试失败不作已修复宣称；真实 WeLink 内网取数及打包安装验收仍待补充。

## 3 WeLink 手机入口复用研究

对方采用本人账号的指定群作为通道，不要求建立独立的企业机器人应用：手机发到群，电脑侧通过 CLI 读取并以同一登录账号发回群。

1. 用户选择群并启用，保存 groupId、启用时间和授权账号。
2. 每 6 秒按群消息游标查询更新；默认仅识别本人 UID，另可显式授权额外账号。
3. 过滤已见消息、程序自己发送的前缀与内容哈希、非文字、启用前或超过 120 秒的旧消息；限制每分钟接收量。
4. 将文字交给公司助理队列，记录待答状态；通过会话工具可查进度、新建任务、补充要求、停止和关注结果。
5. 回复去除部分 Markdown，按约 1500 字分段，经串行发送队列发回指定群，并检查 CLI 退出码与业务返回。
6. 被关注任务完成或卡住时推送；出错后退避，登录恢复后继续。

可复用内容是渠道适配、账号核验、去重、会话路由和交付回执。对方发送队列本身是内存 Promise 链；不能据此宣称具备跨崩溃的持久发件箱或严格一次执行保证。若用于长期 Bot，建议将 messageId → 请求／任务及回复状态持久化，再绑定稳定主对话；处理重启期间旧消息的策略需单独确定，不照搬 120 秒丢弃规则。图片、文件、语音在这一通道中尚不支持，也不把同仓库其他渠道的多媒体能力算进来。

执行依赖电脑开机未休眠、程序运行、WeLink PC／CLI 可用及内网连接。手机可以在外部收发群消息，不会让已关机的电脑继续执行。

## 4 长期 Bot 与短执行会话

长期身份、用户看到的主聊天、一次执行上下文、后台宿主是不同对象。公司助理每问新建 CodeAgent 执行会话，附上最近两轮、记忆和挑好的业务材料；这不妨碍使用同一个长期助理入口。

Hermes 研究对象为 NousResearch/hermes-agent，以下按 2026-11-17 读取的官方 main 文档：

- Gateway 持续连接消息平台并运行调度；收到消息时按渠道、聊天和用户等路由到持续会话。
- SQLite 保存消息、工具记录和会话元数据；重启后可恢复。进程内 Agent 缓存可释放，不等于聊天历史被清除。
- 活跃模型上下文有长度上限，达到阈值后压缩为摘要及保留片段；当前配置文档的 in_place 默认开启，压缩可保持原会话 ID，旧内容软归档并仍可检索。其他模式可采用延续会话，不能把内部 ID 策略当成永久产品身份。
- USER.md、MEMORY.md 保存有上限的长期信息，session_search 按需找历史。“无限聊天”表示可以持续使用，不表示每次请求都包含全部原话或永不遗忘。
- 当前核心文档不再因每日边界或空闲自动重置，用户可显式 /new 或 /reset；旧定时重置策略迁到插件，不能照抄旧版默认值。
- 24 小时待命仍依赖持续运行的主机；闲置监听不要求持续调用模型。

CMO 已于 2026-11-18 接入稳定 Bot 身份、持续主对话、独立任务上下文及本机 Host，实际能力见 [落地记录](bot-workbench-implementation-2026-11-18.md)。WeLink 手机入口仍 pending，未来只是同一 Bot 的渠道。长期办公归档、材料检索与台账仍保持上表状态，不因 Bot 核心接入而视为已完成。

## 5 会议伴侣

目标：用户明确开始采集后，将屏幕、系统声音和麦克风材料整理为可回查、可修订的会议记录，并支持会中问答。会后行动项先形成待确认建议，沿用现有待办机制。

| 能力 | 规划行为 |
| --- | --- |
| 采集 | 选择窗口或屏幕与区域；系统声音、麦克风可选；开始、暂停、继续、结束状态明确 |
| 转写 | 复用现有 SenseVoice／Silero 基础；按停顿分段处理长会议，不能只去掉当前 120 秒上限 |
| 画面 | 保存变化后稳定的精选截图，去重；录像供用户回看，不逐帧输入模型 |
| 时间索引 | 音频、转写、截图和人工重点使用同一会议时间线，保留采集与转写缺口 |
| 纪要 | 议题、关键事实、决定、行动项、待确认分条保存；固定编号增量新增／修改，不用“本轮无更新”覆盖原纪要 |
| 问答 | 基于提问时刻的材料和纪要回答；能按时间读取早前原话及截图，并与纪要更新分别排队 |
| 发言人与术语 | 保留音轨；分期研究声纹编号、人工命名和专业词纠正，不承诺自动准确识别人名 |
| 会后 | 最终复核、历史回看和导出；负责人、期限未明确时保留未明确，不补造 |
| 业务联动 | 用户确认后才将行动项写入待办；不因会议里有人说“发给某人”就自动执行外部操作 |
| 数据与执行 | 原始材料本地保存；明确哪些转写／截图发送到已配置模型，不将本地 ASR 宣称为全程离线 |

当前入口为「日程待办 → 会议记录 → 会议伴侣」，也可从选中的会议打开。窗口或屏幕、Windows 系统声音和麦克风按需选择。保存的是分段音频和精选截图。截图发送给支持图片的模型需为本次录制启用。纪要追加或修改时校验出处，已保存记录可重开；中断后可补转写。连续录像、按区域采集、暂停续录、声纹识别和术语库仍待完善。

验收重点：

1. 在约定的长会议样本中验证系统声音与麦克风、切段不丢字、停止后尾段排空；预先确定样本、时长与准确率评估口径。
2. 正确显示采集／转写／理解进度，积压、设备断开、写盘失败和模型失败不伪装成功，不丢已保存材料。
3. 修改一个决定只更新对应条目；空回复、无更新或格式异常不能清空既有纪要。
4. 每条关键结论可定位原话或截图；材料缺失、尚未识别和推断单独标明。
5. 会中提问能回查早前内容；长历史通过增量与检索控制输入，不反复发送全部录像与转写。
6. 重启可找回已保存会议和中断状态，不声称自动恢复失效的屏幕／音频授权；迟到结果不串入其他会议。
7. 实机与打包后分别验证录制、识别、模型理解和导出；真实环境验收与夹具测试分别记录。

## 6 出处回查学习

对方取数时先分配来源编号，模型回答引用这些编号；页面将编号渲染为可点标签。后端按当前账号读取原文，消息展示前后各两条上下文、采集时间和覆盖范围。简报会删除找不到原始来源的条目；会议时间、主题继续取原始事实，不让模型重写。

建议复用于消息邮件分析及会议纪要：来源编号由后端产生，保留账号、记录标识、采集时间、查询范围和版本；界面展示可回查证据及是否完整，历史快照标明“当时记录”。来源存在仅说明引用对象真实存在，不自动证明模型结论受原文支持，语义仍需对照原话。

办公资料已保存原话、会话、发送人、业务时间、采集时间和覆盖范围。Bot 的引用由本轮实际取出的资料解析，简报条目只能选择当次候选，时间和主题仍取系统记录。旧简报回查保存时的出处版本。

## 7 实体会议室预约

该功能不是通过 welink-cli meeting create 预约实体会议室，而是集成“秘书终结者”独立 Python／浏览器组件。Hub 保存设置并通过本地 requests／replies JSON 控制组件，组件保留登录和预约执行资源。

核心流程：用户设置星期、时段、时长、优先会议室及开放节奏 → 调度预热并校对服务器时钟 → 浏览器打开表单、读取可用会议室并选时段 → 到开放时刻提交 → 按新出现的业务提示判断成功、被抢、失败或未知 → 保存历史、日志及后续动作。首选被抢时可换下一间；按钮消失而没有成功提示时仍是结果未知。

组件提供不动作／通知／自动释放等模式。具体后续动作依赖原组件，不根据名称推断释放条件或承诺通知已成功。一次抢订、测试发送和删除待执行动作要求用户页面操作；计划设置与后台守护另有入口。

CMO 从「日程待办 → 会议记录 → 会议室预约」连接兼容组件，保存计划、查房、检查登录、测试条件并在用户确认后发起一次或定时预约。页面监听业务回执、下次放号时间和日志。园区规则、登录、换房竞争及实际预约仍需真实内网验证。

业务目标如下，组件负责实际站点的时钟、页面提交与结果核验。

1. 保存园区、工作日、时段、时长、优先房间与候选顺序；展示下次执行时刻，支持暂停和删除计划。
2. 预约前检查登录、站点与放号规则、服务器时间偏差，提前准备页面；主机离线或休眠错过时刻时说明错过，不伪装已执行。
3. 在用户确认的计划范围内定时提交；首选被占时换候选房间，已有确认单则不重复预约。失败重试有上限。
4. 核对预约单／明确的新成功提示，保留房间、日期、时段及业务编号；没有可核对结果时标为未知，先查询确认再决定重试。
5. 保存运行历史、日志、失败原因与通知；成功结果经确认可进入本地日程。取消和自动释放作为后续独立规则，先核验站点能力和业务条件。

验收包括正常预约、首选被抢后换房、未登录、时钟偏差、断网、未知结果、重复触发、程序重启及错过放号。当前仓库验收覆盖本地协议与模拟业务回执。首次使用请选择已安装的兼容程序或数据目录，安装和升级由组件负责。
